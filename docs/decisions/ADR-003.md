# ADR-003: Estrategia de orquestación y recuperación de fallos

## Contexto
El DAG de Airflow depende de que existan datos válidos en el Data Lake. Si una tarea falla, el sistema debe recuperarse o detenerse de forma controlada para no generar reportes con datos corruptos.

## Opciones consideradas
1. Detener el DAG inmediatamente al primer fallo sin reintentos.
2. Configurar reintentos (retries) y usar XCom para comunicar el estado de calidad.
3. Ignorar el fallo y continuar con las tareas de reporte.

## Decisión tomada
Se implementó la opción 2: configurar reintentos (`retries=4` para `verificar_datalake` y `retries=2` por defecto) y usar XCom. Si la validación falla tras los reintentos, el DAG se detiene y no genera el reporte.

## Evidencia utilizada
Prueba controlada: Se inyectó un `FileNotFoundError` en la función `verificar_capas`. El log de Airflow mostró: `FileNotFoundError: FALLO CONTROLADO: No se encuentran los archivos...`. Al corregir el código, el log mostró el error real de datos faltantes (`Sin archivos Parquet...`), demostrando la recuperación del código y la resiliencia del sistema.

## Consecuencias / Trade-offs
- **Positivas:** Mayor resiliencia ante fallos temporales, y los reportes solo se generan si hay datos reales.
- **Negativas:** Si hay un error de lógica, los reintentos retrasan el fallo final consumiendo recursos.
